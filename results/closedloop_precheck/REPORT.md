5. **폐루프는 대부분 사후 재생으로 구현할 수 있다.** 피드백을 지금처럼 배경 차량에서 받으면 임계값 상태가 대상의 경로와 독립이기 때문이다.

   - 그다음 트립별 상태기계(정상 → 놓침 → 복구 → 재개/상실)를 사후 재생한다.
   - 필요한 변경: 지평 확장 정답 표, 지평 확장 예측기, 복구 질의 스트림과 그룹, 재생기.

## 2. 현재 재생 구조

**(a) hop t의 탐색 시작점: 정답 위치이고, 이전 hop의 결과와 무관하다(개방 루프).**
- hop은 궤적에서 미리 만든다. 에피소드 k의 끝에서 출발 카메라 `src`(마지막으로 끝나는 관측)와 `t_exit`를 정한다(`ccpilot/events.py:113-116`). 다음 에피소드가 T_max 안에 시작하면 그 에피소드의 (카메라, 시간 칸)이 정답이다(`events.py:118-128`).
- 평가는 모든 비-exit hop을 독립 질의로 채점한다: `vm.score(tr_test, truth_map, …)`(`ccpilot/evaluate.py:220`), hit = `s_true >= tau`(`evaluate.py:297`). 탐색 결과가 다음 hop의 시작점이나 시각을 바꾸는 경로는 코드에 없다.
- 유일한 경로 지표인 custody는 같은 개방 루프 hit의 누적 최솟값이다(`evaluate.py:412-430`). 끊긴 뒤의 복구나 그 비용은 반영하지 않는다.

**(b) '재포착(re-acquired)' 그룹의 정의**
- `hopkind = 0`(hop > 0), `1`(hop = 0, chain = 0: 트립의 첫 hop), `2`(hop = 0, chain > 0)다(`evaluate.py:44-46`).
- chain은 exit 전환마다 하나씩 늘어난다(`events.py:135-138`). exit은 다음 에피소드가 T_max(600 s)를 넘겨 시작하거나 다음 에피소드가 없는 경우다(`events.py:117-122`).
- 따라서 **재포착 hop = 같은 트립 안에서 600 s를 넘는 공백 뒤 다시 보인 에피소드에서 출발하는 첫 hop**이다. 그 재등장 자체는 정답으로 주어진다.
- 공백을 만든 hop(`is_exit = True`)은 평가에서 빠진다(`evaluate.py:102-104`). 그러니 개방 루프의 재포착 hop은 "복구 탐색"이 아니라 "정답으로 재획득된 뒤의 첫 정상 탐색"이다.
- 규모: 확증 2 합산 4,390 hop(블록 1,779 / 2,611)으로, 전체 평가 hop의 약 0.4%다.

**(c) 예측기의 경과 시간 입력: 없다. T_max를 넘는 재예측은 현재 불가능하다.**
- `VisibilityModel`의 키는 `levels`의 접두어다. 주 예측기는 (src, zone, hgroup, speed_bin)이다(`ccpilot/predictors.py:51-80`, 설정 `eval.predictors`).
- 행렬은 후보 카메라 × B칸이고, B = ceil(T_max/δ) = 120칸(δ = 5 s, `events.py:89`)이다. 칸은 퇴장 시각부터 잰 시간이다.
- 경과 시간은 칸 위치로만 들어간다. "마지막 확인 카메라에서 시간을 늘려 다시 예측"하려면 B > 120의 행렬이 필요하다.
- 학습 정답도 '다음 에피소드'의 T_max 안 관측뿐이다(`events.py:121-128`, `predictors.py:65-70`).
- 바꿀 것: T_max(=exit 정의)와 분리된 탐색 지평 H를 두고, 지평 H 안의 모든 후속 에피소드 관측을 정답으로 하는 표와 B_H = H/δ칸 예측기를 새로 학습한다.
- 참고: 사후 기하 분석의 `configs/porto_cctv_confirm_geom_tmax900.yaml`은 T_max 자체를 바꿨다. 그래서 exit·재포착의 정의도 함께 바뀌었고, 복구 구현에는 그대로 쓸 수 없다.
- 장애 인지 예측기는 이미 한 단계 합성으로 칸을 이어 붙이지만 T_max에서 자른다(`predictors.py:211-213`).

**(d) 확증 2의 hop별 결과 저장: 있다(로컬, git 제외).**
- 경로: `results/porto_cctv_confirm2/runs/<block>/t<target>/s<seed>/hits.parquet`(50개, `.gitignore:31`로 제외, sha256 목록 `results/porto_cctv_confirm2/runs_manifest_sha256.txt`). 블록 1 한 실행은 534,713행 × 162열이다.
- hop 식별 열: `tr_id`, `trip_id`, `chain`, `hop`, `t_exit`, `segment`(저장 코드 `evaluate.py:335-351`). 그룹 열은 `grp_all, hgroup, hopfirst, hopkind, speed_bin, zone, entropy_bin, nn_bin`이다.
- 방법별 열:
  - `hit|<pred>|<method>`, `cost|<pred>|<method>`: Spatula식은 `spatula_rule|fixed`, CityTrac식은 `citytrac_rule|target<t>`.
  - `score|<pred>`, `kid|<pred>`(비용 조회 키, `cost_lookup_<pred>.npz`), `taumin0.002|<pred>`.
  - `tdet|src_zone_hour_speed|<method>`: 탐지 시각(퇴장 후 초, 8개 방법).
  - `feedback`, `t_res_hit`, `t_res_miss`.
- **원 TRIP_ID 문자열은 hits에 없다.** `trip_id`는 내부 번호(0, 1, …)이고, 원 TRIP_ID는 `work/porto_cctv_confirm2/taxi_map.parquet`의 `trip_key`(열 `trip_id, taxi_id, t0, trip_key`)로 잇는다.
- 출발 카메라·도착 시각은 hits에 없고 `work/porto_cctv_confirm2/transitions.parquet`(`tr_id, trip_id, src, t_exit, zone, speed_out, is_exit, t_arrive, first_cam, chain, hop, …`)에서 `tr_id`로 잇는다. exit hop은 transitions에만 있다.

## 3. 방법별 피드백 요구사항

전제(현재 코드):
- 피드백 hop은 평가 hop 중 무작위 30%다(`fb_mask`, `evaluate.py:140`). 이 hop들은 번호판 등으로 확인된 '배경 차량'으로 간주되고, 정답 점수 전체(관측 라벨 `s_test`, `evaluate.py:221`)를 피드백으로 받는다.
- 해결 시각은 탐지 시 도착 시각, 놓치면 t_exit + T_max다(`evaluate.py:141-143`).
- 대상 차량 자신의 탐색 결과는 어떤 방법에도 들어가지 않는다.
- 아래 '검열 피드백'은 피드백을 탐색 결과에서만 얻는 경우다. 탐지되면 hit와 탐지 위치·시각을 알고, 놓치면 '이 집합에 없었다'(점수 < τ)만 안다.

| 방법 | 온라인 갱신·재적합에 쓰는 정보 | 코드 | 검열 피드백에서의 동작 | 바꿀 것 |
|---|---|---|---|---|
| static | 없음(보정 기간 점수로 한 번) | `calibration.py:46-47` | 영향 없음: 보정 기간 라벨은 과거 자료(완전) | 없음. 복구 질의용 τ를 따로 둘지는 설계 결정 |
| aci_g0005 | 이진 오류(α 갱신) + **정답 점수**(최근 2,000개 창에 추가) | `calibration.py:76-81` | α 갱신은 이진이라 가능. 창에는 `test_scores[j]`를 넣으므로 놓친 hop의 점수가 필요해 그대로는 동작하지 않음 | 창을 검열 자료용 분위수(예: Kaplan–Meier형 하한)로 바꾸거나, hit 점수만 쓰는 편향을 감수. 또는 보정 창을 고정하고 α만 갱신 |
| mondrian_hour_hop_speed | 없음(보정 기간 칸별 점수) | `calibration.py:50-57` | 영향 없음 | 없음 |
| qr_groups | 없음(보정 기간 점수의 분위수 회귀) | `multigroup.py:188-211` | 영향 없음 | 없음 |
| qr_groups_refit | 보정 hop + 해결된 피드백 hop의 **정답 점수**(log)로 매일 재적합 | `multigroup.py:270-289`(라벨 `yt`, 263행) | 놓친 hop은 y < log τ만 알아 그대로는 동작하지 않음 | 좌측 검열 분위수 회귀(예: Portnoy·Peng–Huang형)나 놓친 hop을 τ에서 검열한 점검 손실로 바꿈 |
| qr_groups_refit7 | 같음(최근 7일 창) | 같음 | 같음 | 같음 |
| mvp_log | **이진**(covered = score ≥ τ)과 해결 시각. 웜 스타트·τ 변환은 보정 점수 | `multigroup.py:156-170`, `145-148`, `97-106` | 동작함: 놓쳤다는 사실만 필요(t_exit + T_max에 해결) | 없음(복구 질의를 그룹으로 넣으면 그룹 행렬만 확장) |
| qr_ogd | **이진** err과 해결 시각. 시작값은 qr_groups | `multigroup.py:231-240` | 동작함 | 없음 |
| CityTrac식 | 없음(학습 기간 다음 카메라 비율과 도착 지연 창) | `predictors.py:373-389` | 영향 없음 | 복구 탐색용 창 정의가 없음: T_max 밖 지연 창을 새로 정해야 함 |
| Spatula식 | 없음(학습 기간 비중 ≥ 0.05 카메라, 지연 98% 분위 창) | `predictors.py:310-328` | 영향 없음 | 같음(복구 창 정의) |

- 정답 카메라·시각은 어떤 방법의 갱신에도 쓰이지 않는다. 비용 조회와 평가(`tdet`)에만 쓴다.
- 대상 경로를 폐루프로 바꿔도 피드백을 지금처럼 배경 차량(완전 라벨)에서 받으면 위 표의 '검열' 문제는 생기지 않는다. 검열 문제는 피드백을 대상 탐색에서 얻는 설계로 갈 때만 생긴다.
- 보정 기간 자체도 배경 차량 라벨이라는 가정이다. 이 가정 아래 복구 질의의 반사실 라벨(배경 차량이 hop k에서 놓쳤다고 가정한 복구 탐색의 정답)도 같은 자료에서 만들 수 있다.

## 4. 폐루프 재생의 구현 범위와 실행 시간

복구 규칙(요청): 마지막 확인 카메라에서 경과 시간을 늘려 기존 예측기를 다시 실행하고, 재포착 그룹으로 보정하며, 시간 예산을 넘으면 상실.

### 4.1 핵심 관찰

피드백이 배경 차량에서 오면 임계값 상태(ACI α, MVP V·N, qr_ogd θ, 재적합 계수)는 대상 경로와 독립이다. 따라서 폐루프를 두 단계로 나눌 수 있다.
1. **질의 계산(개방 루프):** 모든 hop k에 대해 정상 질의 N_k(현행)와 반사실 복구 질의 R_k(t_exit + T_max에 src_k에서, 칸 [T_max, H))의 τ·hit·비용·탐지 에피소드를 계산한다.
   - 온라인 방법은 질의 스트림에 R_k를 시간순으로 끼워 넣는다(질의 수 약 2배).
   - R_k의 피드백도 배경 차량(fb_mask)에서 받는다.
2. **경로 재생(사후):** 트립별 상태기계를 돌린다.
   - N_k가 hit이면 k+1로 간다.
   - miss이면 R_k를 실행한다. R_k가 에피소드 j에서 탐지하면 j의 정상 질의로 재개하고, 못 찾으면 상실(트랙 종료)이다.
   - 경로 비용은 실행한 질의 비용의 합이다.
   - 이 단계는 정수 배열 연산이라 실행당 수 분 이내로 본다(확인 필요).
- 복구를 여러 단계(예: 600 s씩 반복 연장)로 하면 R_k^(1..m)이 생겨 질의 수가 (1+m)배가 된다.

### 4.2 필요한 코드 변경

| 영역 | 변경 | 규모(추정) |
|---|---|---|
| 이벤트 | T_max(exit 정의)와 분리된 지평 H. hop마다 지평 안 모든 후속 에피소드의 (카메라, 칸, 에피소드 번호) 정답 표 `truth_h`. exit hop(트립 끝 제외)도 복구 대상으로 포함 | `events.py`에 함수 하나(약 60–100줄). 기본값에서 기존 산출물 불변 |

결정할 것:
- **H**(시간 예산)를 정해야 한다.
- **트립 끝:** 트립의 마지막 에피소드 뒤에는 정답이 없다. 상실로 셀지 검열(트랙 정상 종료)로 볼지 정해야 한다. Porto 자료는 승객 탑승 구간만 있어 트립 사이 차량 위치를 모른다.
- **복구 질의의 그룹:** '재포착 그룹으로 보정'이 현 hopkind=2(정답 재획득 뒤 첫 정상 탐색)와 같은 그룹인지 정해야 한다. 성격이 다르다.
- **평가 기간:** 확증 기간을 쓰면 사후 분석이다. 새 기간은 1.2절의 1월 28일뿐이다.

### 4.3 실행 시간 (확증 2 규모 50 실행)

실측 기준:
- 확증 2 50 실행은 6개 동시로 2026-10-15 17:55 ~ 10-16 18:50, 약 25시간 걸렸다.
- 실행 1회(블록 1, 0.95, 시드 0)는 6개 동시 부하에서 10,244 s였다. 그중 qr_groups_refit 6,979 s, refit7 2,292 s이고, 나머지(예측기 5개, 나머지 방법) 약 970 s다.
- 탐색 1 시험 실행 1회는 7,816 s, 이벤트 단계는 블록당 89 s다.

| 항목 | 추정 | 근거 |
|---|---|---|
| 지평 확장 이벤트·정답 표 | 블록당 수 분 | 현 이벤트 단계 89 s. 정답 행이 후속 에피소드 수만큼 증가 |
| 확장 예측기 학습·채점(주 예측기만) | 실행당 +200–600 s | 행렬 B 3배, 복구 질의 채점 1회. 다른 예측기 4개는 폐루프에서 뺄 수 있음 |
| 재적합 비교군 | 실행당 +0–50% | LP 행 수 상한 80,000(`qr_max_n`)이라 적합 시간은 비슷. 복구 질의 τ 예측은 가벼움. 복구 그룹 열 추가로 LP가 약간 커짐 |
| 온라인 방법(ACI·MVP·qr_ogd) | 실행당 +100–300 s | 질의 스트림 약 2배(Python 루프) |
| 경로 재생 | 실행당 수 분 | 배열 연산 |
| **합계** | 실행당 약 1.2–1.8배 → **6개 동시 50 실행 약 30–45시간** | **확인 필요**: 메모리(현재 실행당 RSS 약 3.5 GB, 확장 예측기로 증가 가능)와 다른 작업의 CPU 점유에 따라 달라짐 |

- 재적합 비교군과 다른 예측기를 빼고 폐루프 핵심(static, ACI, Mondrian, qr_groups, mvp_log, qr_ogd, 두 기준선)만 돌리면 실행당 약 0.3시간, 50 실행 6개 동시로 약 3–5시간이다(확인 필요).
- 재적합 시간이 전체를 지배한다.
- 메모리가 실행 수 상한을 정할 수 있다. 지금도 보류 기간 재분석 6개가 31 GB 중 27 GB를 쓰고 있다.
